# Adversarial Architecture & Modern Practice Audit Report

## 1. エグゼクティブサマリー（辛口評価）

業界のモダン水準（2025〜2026年標準）に照らし合わせた現在の到達度は、**「限定的かつ表層的」** と言わざるを得ません。
プロジェクトは「GASのランタイムエラー0」「Jestによるユニットテスト駆動」など、一定の品質ラインを志向している形跡は見られます。しかし、実態としては以下のような重大なギャップを抱えています。

- **AIガバナンスとドキュメントドリフト:** `AGENTS.md` の制約は部分的にしか守られていません。特に「過剰分割された自明なマイクロ関数を作らない」というルールがあるものの、エクスポートガード周りや共通処理で依然として手続き的・冗長な実装が散見されます。
- **テストの殺傷力不足:** カバレッジの数値（Branches 80%+）は達成されていますが、`mockGasEnvironment.js` が極めて限定的（Happy path寄り）であり、GAS本番環境でのQuota制限、トリガー重複実行、LockServiceのタイムアウトといった「本当のクラウド障害」を再現できていません。
- **CI/CDとデプロイの旧態依然:** GitHub Actionsの運用が静的解析と単体テストに留まっており、デプロイやリリース管理（セマンティックバージョニング、CHANGELOGの自動生成など）が完全に手動・属人化しています。
- **トランザクション整合性の脆弱さ:** スプレッドシート操作における `deleteRows` の事前検証など、一見防御的に見えますが、並行処理や部分的な失敗時のロールバック機構が欠如しています。

総評として、本リポジトリは「ホビー用途としては及第点」ですが、「シリアスなIoTデータ基盤」としては耐障害性と自動化の観点で深刻な技術的負債を抱えています。

## 2. 致命的・中程度のリスク一覧（Findings）

### 2.1. GASモックの限界による本番障害のマスキング
- **ファイル:** `tests/helpers/mockGasEnvironment.js` (全体)
- **現状の甘さ／リスク:**
  モックが `appendRow` の失敗を部分的にシミュレートできる（`failDailyAppend`等）以外、GAS特有の厳しい制限（6分間の実行時間制限、API呼び出しのQuota超過、LockServiceのタイムアウトによる後続処理の中断）を再現する能力がありません。これにより、テストが通っても本番で突然死するリスクが放置されています。
- **改善案:**
  Quotaシミュレータを導入し、一定回数以上の `SpreadsheetApp.openById` や `UrlFetchApp.fetch` 呼び出しで例外を投げるようにモックを強化する。また、`LockService` のモックに確率的なタイムアウトを注入する。

### 2.2. CIパイプラインの非効率性と欠落
- **ファイル:** `.github/workflows/ci.yml` (Line 13-43)
- **現状の甘さ／リスク:**
  `npm ci` のキャッシュ設定は `setup-node` の機能で実装されていますが、依存関係の更新がない場合でも全体の検証ステップに無駄な時間がかかっています。さらに致命的なのは、ファームウェア（`firmware/esp8266_bme280_gas_logger/`）側のC++コードに対するコンパイル検証（Arduino CLI等を用いたテスト）がCIに組み込まれていない点です。これにより、C++側の破壊的変更が素通りします。
- **改善案:**
  Arduino CLI アクションを追加し、ESP8266 ターゲット向けのコンパイルチェックを CI ジョブに必須とする。

### 2.3. 排他制御のタイムアウトとフォールバックの甘さ
- **ファイル:** `gas/DataArchive.gs` (Line 60-70)
- **現状の甘さ／リスク:**
  `LockService.getScriptLock().waitLock(timeoutMs)` を使用していますが、ロックを取得できなかった場合（例外発生時）のリカバリ・リトライ処理が存在しません。GASのトリガーが重複して走った場合、例外が投げられてデータアーカイブが完全にサイレント失敗する可能性があります。
- **改善案:**
  ロック取得失敗時のカスタムエラー設計を実装し、Cloud Logging / エラー通知へエスカレーションする。またはExponential Backoffによるリトライを組み込む。

### 2.4. LINE APIの200通枠枯渇リスクの境界値設計
- **ファイル:** `gas/Metrics.gs` (Line 233-272)
- **現状の甘さ／リスク:**
  `evaluateAlertDecision_` で1日5回の送信上限が実装されていますが、これは「1日に5回」というローカルな制限であり、「月に200回」というLINEの絶対的な無料枠上限を意識した全体アーキテクチャ（月次での送信可能残数の管理）が存在しません。月末に異常が連続した場合、通知が届かなくなるリスクがあります。
- **改善案:**
  PropertiesService に `MONTHLY_ALERT_COUNT` を追加し、月ごとの絶対上限（例えば180回）を設定するガード節を `evaluateAlertDecision_` の先頭（優先順位）に組み込む。

## 3. 過剰な装飾・アンチパターンの指摘

`AGENTS.md` には「複雑度を下げるためだけに、単なるオブジェクト生成や1行の比較式などの自明なマイクロ関数を乱立・細分化しない」と明記されていますが、一部でこのルールが形骸化しています。

### 3.1. 過剰抽象化とマイクロ関数の乱立
- **ファイル:** `gas/Router.gs`
- **指摘:**
  `successResponse_()`, `errorResponse_(errorCode)`, `readinessResponse_(ready)` といった関数群は、最終的にすべて `jsonResponse_()` を呼び出しています。これはまさに「自明なオブジェクト生成のマイクロ関数」の典型例であり、スコープを無駄に汚染し、逆に追跡可能性（Traceability）を低下させています。
- **本来あるべき姿:**
  ルーティング関数内で直接 `jsonResponse_({ ok: true })` のように記述すべきであり、中間関数は削除すべきです。

### 3.2. 不自然なエクスポートガードの散布
- **ファイル:** 全ての `.gs` ファイル
- **指摘:**
  各ファイルの末尾に `if (typeof module !== 'undefined') { module.exports = { ... }; }` が定型文として挿入されています。これはGASとNodeの二重環境を維持するための苦肉の策ですが、モジュール間の依存関係がGASの暗黙のグローバルスコープに依存しているため、テスト時（Node環境）と本番時（GAS環境）でシンボルの解決方法が異なるというアーキテクチャ上の深い歪みを生んでいます。

## 4. モダン化ロードマップ（優先度別）

### High（即座に対応すべきリスク）
1. **ファームウェアのCIコンパイル検証追加**
   - リスク: C++コードの破壊的変更の素通り。
   - タスク: `.github/workflows/ci.yml` に Arduino CLI を用いたビルドジョブを追加。
2. **LINE月間送信上限（Monthly Limit）ガードの実装**
   - リスク: 200通無料枠のサイレント枯渇。
   - タスク: `evaluateAlertDecision_` のロジックに月次カウント（`PropertiesService`）のインクリメントとチェックを追加。

### Medium（中期的な改善）
1. **ルーティング層のマイクロ関数駆除（リファクタリング）**
   - リスク: 可読性の低下と `AGENTS.md` 違反の常態化。
   - タスク: `Router.gs` 内の過剰なレスポンスラップ関数をインライン化し、複雑度ペナルティを受けずに平坦化する。
2. **GASモックの堅牢化（Quota & Timeout 注入）**
   - リスク: 本番環境の限界をテストできない。
   - タスク: `tests/helpers/mockGasEnvironment.js` に意図的なLockService例外や実行時間制限シミュレーションを実装。

### Low（余力があれば対応）
1. **デプロイパイプラインの完全自動化**
   - 現状の `npm run deploy`（手動スクリプト）から、GitHub Actions上の `google/clasp` を用いた自動デプロイメント（本番マージ時）への移行。
2. **エラーハンドリングの Observability 向上**
   - 現在のシートベースの `ErrorLog.gs` に加え、重大なエラー（Lock取得失敗など）時のLINE管理者向けダイレクトエラー通知機構の導入。
