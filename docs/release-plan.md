# リリース計画

GAS Web Appの本番リリースおよび旧システム廃止までの全体手順・判断基準を整理する。

---

## 1. 前提条件

- **現行稼働状態**: 受信基盤（Phase 0〜6）の GAS Web App が本番稼働中であり、ファームウェアは `v1.0.0-stable` で動作している。
- **GASプロジェクト構成**: 1つのGASプロジェクトのまま `.gs` ファイルを機能ごとに分割して拡張する（Router / Ingest / Monitor / DailyAggregation / MonthlyAggregation / LineBot / Config / ErrorLog）。
- **URL維持**: ESP8266の宛先URLはビルド時に固定されるため、本番Webアプリの `/exec` URLを変更しない。既存デプロイを同じデプロイIDで更新する（`docs/deployment.md` のURL固定ルールに従う）。
- **承認プロセス**: 本番デプロイ・LINE設定・実機書き込み・旧システム最終廃止は、人間の承認後に実施する。
- **手順の整合性**: デプロイ手順は `docs/deployment.md` の本番デプロイ手順と整合させる。

---

## 2. リリース単位

`v1.0.0-stable` 以降は、機能単位で段階的にリリースする。旧システム（ambidata / 日別シート / LINE旧コード）への依存は残さず、ambidata APIは扱わない。

| リリース | 内容 | 依存Phase |
| --- | --- | --- |
| v1.1.0 | 重複排除・Router/Ingest 分割 | 7（決定）, 8, 9 |
| v1.2.0 | 環境監視（Monitor.gs） | 10（決定）, 11 |
| v1.3.0 | LINE Bot（LineBot.gs） | 12, 13 |
| v1.4.0 | 日次集計（DailyAggregation.gs）・Config/ErrorLog | 14（決定）, 15, 16 |
| v1.5.0 | ウォッチドッグ・月次ロールアップ（MonthlyAggregation.gs） | 17, 18, 19 |

## 3. 本番デプロイ手順

以下の順序に従って本番反映を実施する。

1. **環境準備**: 必要に応じてDailyシート・Configシートを用意する。
2. **タイムゾーン設定**: タイムゾーンを `Asia/Tokyo` に維持する。
3. **ソースコード反映**: GASプロジェクトに `gas/` 配下のモジュール（Router / Ingest / Monitor / DailyAggregation / MonthlyAggregation / LineBot / Config / ErrorLog）を反映する。
4. **プロパティ設定**: Script Properties に必要なキーを設定する（閾値などはConfigシート採用時はそちら）。
5. **事前検証**: `/dev` のテストデプロイで動作確認を行う。
6. **本番デプロイ**: 本番は既存の `/exec` デプロイを同じデプロイIDで更新し、URLを維持する。
7. **URL確認**: 更新前後で `/exec` URL が同一であることを確認する。
8. **外部連携・トリガー**: LINE Webhook / 定時トリガー（日次集計）を設定する。
9. **動作確認**: 正常系・異常系のスモークテストを実施する。
10. **結果記録**: スモークテスト結果を秘密情報を含まない形で `docs/test-results/` に記録する。

## 4. ロールバック（障害時の対応方針）

### 4.1 ロールバック方針

| 観点 | 方針 |
| --- | --- |
| 切り替え | 旧システムは停止済みのため、旧環境への並行稼働切り戻しは行わない |
| 復旧 | 問題発生時は新システム内で修正し、デプロイを過去バージョンへ戻した上で修正版を再適用する |
| 追加機能 | 監視・LINE・日次集計は受信基盤に対する追加。受信（DATA追記）に影響が出た場合は、まず受信基盤の正常バージョンへ戻す |

### 4.2 ロールバック手順

1. 直前の正常バージョンを確認の上、GASの **「デプロイを管理」** から同じデプロイIDで以前の正常バージョンへ戻す。
2. 更新前の `/exec` URL に対して `curl` 等を用いて応答・動作を確認する（URLは変わらない）。
3. 不具合の原因調査と修正を実施する。
4. 再デプロイ前に `/dev` 環境で検証を完了させた後、再度本番へ反映する。

## 5. 旧システム廃止条件

以下のすべての条件を満たした時点で、旧システムの完全廃止を決定する。

- 新システムが最低1週間安定して動作していること
- データ欠損および重複が許容範囲内であること（重複排除が働いていること）
- 通知および環境監視機能が安定して稼働していること
- 人間による旧システム廃止承認が得られていること

---

## 6. 人間による承認が必要なタイミング

以下のフェーズへ進む際は、必ず担当者（人間）による確認と明確な承認を要する。

- スプレッドシート構成の最終決定（DATA列・Dailyシート・Configシート）
- Script Properties のキー / 値の決定、閾値・平滑化・簡易暑さ指数の式の確定
- 本番 Web App のデプロイ実行
- LINEチャネル設定 / Webhook設定の変更
- 本番環境への切り替え
- 旧システムの完全廃止

---

## 7. リスクと対策

| リスク | 対策 |
| --- | --- |
| 通知がサイレントに止まる | DATA書き込みと通知を分離し、通知側を try/catch で保護。トリガー失敗通知メールを有効化 |
| 重複POSTの放置 | Ingest.gs の重複排除（最終行参照・時間窓） |
| LINE月間無料枠の消費 | 状態遷移方式（超過時1回のみ。Replyは非カウント / Pushはカウント） |
| 秘密情報のログ出力 | ErrorLog.gs でHTTPメソッドとホスト程度のみ出力 |
