# リリース計画

GAS Web Appの本番リリースおよび旧システム廃止までの全体手順・判断基準を整理する。

---

## 1. 前提条件

- **旧システムの状態**: 既に停止済みであり、新旧システムの並行稼働は行わない。
- **承認プロセス**: 本番デプロイおよび旧システムの最終廃止は、人間の承認後に実施する。
- **手順の整合性**: デプロイ手順は `docs/deployment.md` の本番デプロイ手順と整合させる。

---

## 2. 本番デプロイ手順

以下の順序に従って本番反映を実施する。

1. **環境準備**: スプレッドシートを作成し、DATAシートの先頭行を用意する。
2. **タイムゾーン設定**: タイムゾーンを `Asia/Tokyo` に設定する。
3. **ソースコード反映**: GASプロジェクトを作成し、`gas/Code.gs` を反映する。
4. **プロパティ設定**: Script Properties に必要なキーを設定する。
5. **事前検証**: `/dev` のテストデプロイで動作確認を行う。
6. **本番デプロイ**: 本番は既存の `/exec` デプロイを更新し、URLを維持する。
7. **URL確認**: 更新前後で `/exec` URL が同一であることを確認する。
8. **外部連携・トリガー**: Webhook / LINE / 定時トリガーを設定する。
9. **動作確認**: 正常系・異常系のスモークテストを実施する。
10. **結果記録**: スモークテスト結果を秘密情報を含まない形で `docs/test-results/` に記録する。

---

## 3. ロールバック（障害時の対応方針）

### 3.1 ロールバック方針

| 観点 | 方針 |
| --- | --- |
| 切り替え | 旧システムは停止済みのため、旧環境への並行稼働切り戻しによるロールバックは行わない |
| 復旧 | 問題発生時は新システム内で修正し、デプロイを過去バージョンへ戻した上で修正版を再適用する |

### 3.2 ロールバック手順

1. 直前の正常バージョンを確認の上、GASの **「デプロイを管理」** から以前の正常バージョンへ戻す。
2. 更新前の `/exec` URL に対して `curl` 等を用いて応答・動作を確認する。
3. 不具合の原因調査と修正を実施する。
4. 再デプロイ前に `/dev` 環境で検証を完了させた後、再度本番へ反映する。

---

## 4. 旧システム廃止条件

以下のすべての条件を満たした時点で、旧システムの完全廃止を決定する。

- 新システムが最低1週間安定して動作していること
- データ欠損および重複が許容範囲内であること
- 通知および環境監視機能が安定して稼働していること
- 人間による旧システム廃止承認が得られていること

---

## 5. 人間による承認が必要なタイミング

以下のフェーズへ進む際は、必ず担当者（人間）による確認と明確な承認を要する。

- スプレッドシート構成の最終決定
- Script Properties のキー / 値の決定
- 本番 Web App のデプロイ実行
- LINE / Webhook 設定の変更
- 本番環境への切り替え
- 旧システムの完全廃止
